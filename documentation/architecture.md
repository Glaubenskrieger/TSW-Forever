# Architecture overview

Technical background for contributors. Packaging is in `packaging.md`, versions in `versioning-policy.md`, security in `security.md`, third-party components in `third-party-components.md`.

## 1. Components
| Folder | Program | Role |
|---|---|---|
| `launcher/` | `tsw-launch` | command-line launcher and installation manager (Rust); contains the shared logic |
| `launcher-gui/` | `tsw-launcher` | graphical front end (Rust, Slint), calls `tsw-launch` from its own folder |
| `patcher/` | `tsw-patch` (crate) | signed client-patch engine, embedded in both programs |

Central project configuration (version, URLs, app ID) is `packaging/project.conf`, mirrored by `launcher/src/project.rs`; a test keeps both equal.

## 2. Settings
A setting has exactly one source. Game values stay in the game's own preferences (`Prefs_3.xml`), which the game writes itself; the launcher stores only what the user explicitly chose and writes game values only then. Launcher settings live in `~/.config/tsw-launch/` (`config`, `install-state`, `last-launch.txt`); unknown keys of the GUI are known to the CLI so older and newer files stay valid.
* **Launcher language:** `.po` catalogue per language in `launcher-gui/translations/<lang>/LC_MESSAGES/tsw-launcher-gui.po` (English is the source and fallback; German is translated), selectable at run time (`language = auto|de|en`). A new language is one `.po` file plus one line in `i18n::LANGUAGES`; tests demand completeness and identical placeholders. CLI messages are English; the GUI translates them through stable codes.
* **Resolution:** `game_resolution = WxH` is an opt-in, persisted GUI setting. Connected active outputs are queried read-only through XRandR in Wine's actual display environment (X11/XWayland/nested Steam compositor), bounded to two seconds. Modes are validated, deduplicated and sorted by area; no physical-DRM fallback invents modes unavailable to a nested compositor. No display connection means only the game-managed GUI entry is offered. Every launch revalidates a saved choice; an unavailable mode is refused with a message, never silently substituted.
* A selected mode uses the existing `wine explorer /desktop=TSW,WxH <client>` path and writes the same size to the existing **per-user** `DisplayResolution` preference. It does not modify original game binaries/data or call output configuration tools. The private Wine desktop isolates the game display; there is no host-mode restoration step. No Gamescope dependency is introduced. The hidden legacy Gamescope option cannot be combined with manual game resolution and is refused explicitly. Existing explicit CLI `--resolution` and `--virtual-desktop` options retain their semantics. Selecting the new game-managed entry stores `game_resolution = game`. Either new display choice takes precedence over legacy display/Gamescope configuration without deleting those stored keys; old configurations retain their behaviour until a new display choice is made.
* With no explicit option the launcher no longer substitutes the monitor's preferred size or overwrites the game's saved resolution. That previous DRM fallback caused the reported return to 4K on the Steam Machine. The rc.3 private-desktop behaviour needs its own practical Steam Machine test; unit tests and read-only discovery are not game-runtime validation.
* **Window management:** `wm_decorations = auto|on|off` (`--wm-decorations`); by default Wine/Proton games start without window-manager decoration (`WINE_NO_WM_DECORATION=1`). Without it, Alt+Tab in exclusive full screen returned the game as a tiny 113×28 window (second `WM_SIZE` while KWin decorated the window); verified with real Alt+Tab cycles (13/13 with the fix, 7/7 failures without).

## 3. Graphics
The normal start needs no Gamescope. Gamescope is optional (`gamescope = true`, `--gamescope`; the GUI card is hidden in rc.3) and runs with identical internal and output resolution, so there is no scaling and the UI keeps its size. FSR is not offered: it scales the finished picture including menus and HUD, and The Secret World cannot render the HUD at a separate resolution (measured: UI factor 1.47 with Gamescope FSR, 1.00 without). Old `fsr*` keys are read and ignored. If Gamescope is switched on but missing, the start is refused with a clear message (no silent fallback); it cannot be combined with the virtual desktop. Direct3D components and the shader cache are covered in `third-party-components.md` and the `prefix`/`shadercache` modules.

## 4. Installation
Everything managed lives under `~/Games/The Secret World` (`install::Layout`, identical on the host and in the Flatpak):
```
prefix/     Wine prefix; the game lives directly inside: prefix/drive_c/Program Files (x86)/Funcom/The Secret World/
runtime/    GE-Proton (downloaded by the launcher, SHA-256 verified)
downloads/  Funcom installer (can be downloaded again)
cache/      native/ (verified Direct3D DLLs), patches/ (working folder of the patch system)
logs/       diagnostic logs
```
Layouts under `~/.var/app/…/data/…` are legacy: reported by `install status`, never used, changed or migrated.

**Flow (GUI main view, CLI `tsw-launch install …`).** One consent covers the downloads (original installer, runtime, Microsoft components, about 700 MB). The button "INSTALL THE GAME" (or "CONTINUE INSTALLATION") runs the standard sequence: create folders → download and verify the installer → runtime → prefix and shader profile → start the **original Funcom installer**; every finished step triggers the next until the original installer shows its own dialogs (the user keeps the default settings and path). The original Funcom patcher then downloads the game data itself and resumes after a restart; TSW-Forever has no download manager for that. An existing installation can be adopted in place (`install adopt`). Folder creation refuses relative paths, `.`/`..`, system folders, the home folder and its parents, symlinks and foreign non-empty folders.

**Downloads** run through `curl` as a subprocess (argument vector, no shell, certificate checks on, https only also after redirects, at most 3 redirects, timeouts), resume a `.part` file (`-C -`), get their final name only after the SHA-256 matches and are discarded otherwise.

**State** is derived from the file system (`install::assess`: Empty → FoldersReady → PartialDownload → InstallerReady → PrefixReady → Installed); only user decisions are stored, so a crash or deleted folder can never leave a false "installed".

### Completion detection
Game files alone (client executable, `RDB/RDBHashIndex.bin`) do not mean a finished installation: the index is complete from the first second and the data containers are pre-sized. The only reliable mark is the original patcher's own verdict at the start of a run (`Patcher.log`: `Old roothash == New roothash` and zero new/changed/deleted resources and downloads), parsed by `launcher/src/patchlog.rs` (only these fixed lines are read, the last run wins). Around it:
* A watcher (every second, installation mode only, non-blocking) reads the verdict and the Funcom processes (`install::gate`, shared by GUI and CLI). While a Funcom program works without confirmation the button reads "FUNCOM IS WORKING …" and is locked; after a run without confirmation it offers "VERIFY INSTALLATION" (a visible check run of the original patcher). On confirmation the launcher adopts the installation by itself.
* The launcher closes the patcher **it started** only after Funcom's own confirmation, with no installer running and a quiet log: gently (`wine taskkill /im ClientPatcher.exe` without `/F`, in the managed prefix), once per run, waiting at most 15 s. Otherwise the window stays open and a message says so.
* After a real download the patcher writes no final line. The end is recognised when the patcher shows its "ready" event (Wine thread `audio_client_ma`, appears after the last bulk write) and then writes nothing large (`install::RunWatch`: ready thread plus at least two quiet one-second observations). This rests on measurements (six download runs, never a wrong result), not proof. Without a sound server the event does not appear; the safe path is then to close the Funcom window and use "VERIFY INSTALLATION".
* The CLI cannot observe a patcher run; `install status`/`finish` use the same gate and say so, and `finish` refuses without evidence unless the user names the client (`finish --client`).

### Start
On a successful start the launcher minimises itself and closes when the game ends (also after a crash); on a start error the window stays and shows the error. `tsw-launch --detach --stay-alive` waits for the client and ends the process tree if only an orphaned Wine helper remains.

## 4a. Native Windows
The same code base builds for `x86_64-pc-windows-msvc`. Platform differences are kept in one place, `launcher/src/winnative.rs`: pure functions fed by an environment map (per-user data folder `%LOCALAPPDATA%\TSW-Forever`, default and Steam game folders, command lines for elevating installers, process listing, Direct3D library detection) and a `Capabilities` value that the CLI and the GUI consult (`wine_runtime`, `fps_limit`, `microsoft_components` are off on Windows). On Windows the game is a plain client in a normal folder: there is no Wine prefix, runtime download, shader cache, Microsoft-component provisioning or DXVK setting, and the Slint property `windows` hides those items. The install state machine skips the prefix/runtime/Microsoft steps (`install::assess_native`); installer and patcher are Funcom's own programs, started through the shell so Windows can ask for permission, and completion still comes from the patcher log. Nothing Microsoft is downloaded; missing Direct3D libraries only produce a warning. Details: `building-windows.md`.

## 5. Diagnostics
Nothing is sent anywhere; there is no telemetry. A local startup report `last-launch.txt` (mode `0600`, replaced at every start) records prefix, runtime version, virtual desktop, resolution, `WINEDLLOVERRIDES`, component MD5s, masked start arguments and the names (not values) of extra environment variables. `tsw-launch doctor` checks the environment (32-bit libraries, Vulkan, `ntsync`, gamescope, runner). Verbose diagnostics (Settings → Diagnostics) write masked logs to `<base>/logs/`. `launcher/src/diag.rs` defines the event vocabulary (`Category`, `Severity`, `Recorder`); a user-triggered reduced diagnostic package is implemented by `main::run_diag` and `diaglog::bundle`, also available from the GUI. Saved environment values are omitted structurally; all attachments still require user review. Rules: events carry no user paths, environment values, command lines or file contents (`security.md`).

## 6. Client patch system (inactive)
`tsw-patch` fetches `manifest.txt` and `manifest.txt.minisig` over https, verifies the minisign signature (Ed25519 over BLAKE2b-512, prehashed `ED`), plans file by file against the expected state, verifies every artefact against the **signed** hashes, builds new files in staging, keeps a backup and a journal, swaps atomically per file, re-verifies everything and only then writes the patch level. Guarantees (each covered by tests of the patcher crate): rejected signatures, hostile paths (absolute, `..`, protected names such as `Prefs_3.xml` or `ClientLog.txt`, protected roots such as `RDB/`), symlink checks, hash failures abort before any change, rollback and crash recovery, no downgrade or replay, no update while the game runs, a lock against two updaters, offline-safe (a network error only yields a hint). Manifest format (`tsw-forever-patch 1`): `version N`, `requires M`, `artifact <name> <sha256> <size>`, `file new=<sha> size=<n> [full=<artifact>] [from=<sha> delta=<artifact>] path=<relative path>`; no directive can express a command. Deltas use an own format (`TSWD1`). The system is **off** while `project::PATCH_PUBLIC_KEY` is empty, and the game start is then unchanged. Patch releases are built on the maintainer's machine (see `packaging.md`). Distributing changed original files needs legal clarification first (`third-party-components.md`). Not tested: real patches against a real client and signatures from a real `minisign` binary (tests sign with OpenSSL in the same format).
