# Packaging, CI and releases

How TSW-Forever is built, packaged and released. Release rules (versions, tags, channels) are in `versioning-policy.md`; trust and secrets in `security.md`; third-party components in `third-party-components.md`.

## 1. Formats
| Format | Build | Notes |
|---|---|---|
| Flatpak `org.tswlauncher.Launcher` | `scripts/build_flatpak.sh` | official Linux binary format; not published on Flathub |
| Source archive | `scripts/native_stage.sh` | deterministic `tsw-forever-<version>-src.tar.gz`; Git source is also available |

There are no distribution-specific Linux packages. The native Windows build has its own per-user installer (`packaging/windows/`, Inno Setup; see `building-windows.md`); it is a separate operating system, not a Linux distribution package. No artifact contains game data, Funcom or Microsoft files, or a Wine/Proton runner. The Flatpak app ID must remain unchanged to preserve update identity.

## 2. Flatpak
* Runtime Freedesktop 25.08, SDK extension `rust-stable`, 32-bit support through `--allow=multiarch` (the game client is a 32-bit program). Programs: `/app/bin/tsw-launcher` (GUI) and `/app/bin/tsw-launch` (CLI, in the same folder so the GUI finds it).
* **Sandbox permissions** (`finish-args`, each one needed): `--socket=x11`, `--socket=wayland` (GUI, and Wine through XWayland), `--device=dri` (GPU), `--socket=pulseaudio` (audio), `--share=network` (game servers, downloads, update check), `--share=ipc` (X11 shared memory), `--allow=multiarch`, and exactly one folder: `--filesystem=~/Games/The Secret World:create`. No home, no `~/Games` as a whole, no Steam folder, no `--device=all`, no system or session bus, no `flatpak-spawn --host`. `scripts/check_flatpak_package.py` rejects anything else.
* **Data:** everything managed lives in `~/Games/The Secret World/{prefix,runtime,downloads,cache,logs}`; settings in `~/.var/app/org.tswlauncher.Launcher/config/tsw-launch/`. A Flatpak update only replaces `/app`. `flatpak uninstall --delete-data` removes the app data directory but not `~/Games/The Secret World`.
* **Wine/Proton:** not in the package. The launcher downloads a pinned GE-Proton archive (SHA-256 and size compiled in, https from GitHub) after explicit consent, verifies it before unpacking (only the expected root folder, no `..` or absolute paths) and installs it atomically into `<base>/runtime`. An existing runtime is never replaced.
* **Launcher update:** none by the launcher itself (decision 2026-11, version 0.4.1). The bundle installs no remote with an address and no update portal client exists. When a newer stable release is published, the launcher shows a notice whose button opens `<site>#download-linux` of the web site; the user downloads the newer bundle and installs it over the old one with `flatpak install --user ./tsw-forever-<version>.flatpak` (section 5a). Only a RELEASE build of the Flatpak asks (build metadata `TSW_RELEASE_BUILD=1`, not the branch name); a developer build, a native run and testing packages show nothing.
* **Build:** `scripts/build_flatpak.sh` has the steps `stage`, `fetch`, `vendor`, `test`, `check`, `build`, `bundle` (offline after `fetch`/`vendor`). Fixed inputs: runner `ubuntu-24.04`, Freedesktop 25.08, `Cargo.lock` with `--locked`, vendored crates, `SOURCE_DATE_EPOCH`. Not fixed: apt package state on the runner and the Flathub state of the runtime branch.

## 3. Source archive
`scripts/native_stage.sh` selects the three Rust crates, lockfiles, UI, translations, icons, licences, install script and build instructions. It normalises entry order, owner, timestamps, modes and locale and uses `gzip -n`. No vendored libraries are included. See [`building-from-source.md`](building-from-source.md) for dependencies, building, offline vendoring and installation with `scripts/install_native.sh`.

A source build uses the host's 32-bit Wine dependencies and Vulkan drivers; `tsw-launch doctor` reports missing libraries. External tools include `curl`, `tar`, `gzip`, `bsdtar`, `cp`, `sh` and optionally `gamescope`. The source-built programs run outside the Flatpak sandbox.

## 4. CI workflows (`.github/workflows/`)
| Workflow | Trigger | Does | Must not |
|---|---|---|---|
| `ci.yml` | every push and pull request, manual (`full`) | format, Clippy (`-D warnings`), Rust and policy tests, tests of the development feature `windows-self-update` (same target folder), the Flatpak bundle end-to-end test (`scripts/e2e_flatpak_bundle.sh`, only when Flatpak, script, workflow or Rust files changed), secret scan, prepublication and static Flatpak checks; on main it then CALLS `flatpak.yml` (`needs: checks`), and a manual run with `full` also calls `windows.yml` | publish, use secrets, build a package outside main or before its own checks passed |
| `flatpak.yml` | called by `ci.yml` on main after all checks are green (`tests-passed`), or manual (then with its own tests) | checks, vendoring, Flatpak build and bundle artifact | publish, use secrets, build other refs, be started by a push itself |
| `rc-artifacts.yml` | manual only | Flatpak and source archive, reproducibility, offline source compilation check, installed-bundle version and content audits | create releases, push, tag, use secrets or write permissions |
| `build.yml` | every push to `main`; manual on `main` or an existing tag | BUILD ON PUSH: calls `flatpak-stable-build.yml` (Flatpak bundle and source archive) and `windows.yml` (installer), writes `candidate.json` (SHA-256 of every artifact, kept 30 days), and, independent of that, tests and deploys the static web site to GitHub Pages (job `site`, tip of `main` only) | create a release, tag or commit, sign, use secrets or environments, put anything but the web site on Pages |
| `release.yml` | an owner-pushed tag `vMAJOR.MINOR.PATCH` only (no manual start, no other trigger) | RELEASE ON TAG (section 5, `release-pipeline.md`): verifies the candidate of the build run of exactly that commit (compiles nothing), waits for the approval of the whole release (environment `flatpak-release`), fills a DRAFT with the four files, publishes it only behind the second approval (environment `release-publish`) | build, use secrets or keys, touch GitHub Pages, push, tag, touch a published release |
| `flatpak-stable-build.yml` | called by `build.yml` | tests, the release Flatpak bundle (branch `local`, release build metadata; installed once and audited), source archive | sign, publish, use secrets, environments or write permissions |

**CI structure and cost rules (since 2026-11-16).** One run per commit owns the tests; nothing is tested twice: `ci.yml` runs every check, then on main (for changes that can reach the package: Rust crates, `packaging/`, `scripts/`, `.cargo/`, workflows) its job `flatpak` calls `flatpak.yml` with `needs: checks`, so the expensive package build starts only after every check of the same commit is green and the build workflow skips its own test step (`tests-passed`; a manual run of `flatpak.yml` still runs them). A reusable test workflow or a query for an earlier successful run were considered and rejected: `workflow_run` triggers are forbidden by the policy test, `needs` cannot cross workflows, and waiting for another run costs billed minutes. Optional parts are skipped only when nothing of their area changed (the "Decide" step of `ci.yml`: documentation-only changes skip the Rust feature tests; the end-to-end test needs Flatpak, signing, script, workflow or Rust changes; a new branch, an unknown or rewritten history range and a manual `full` run do everything; always run: version/pin check, formatting, Clippy, the Rust and Python tests including the i18n completeness tests, the secrets and prepublication scans, the policy checks and the static Flatpak validation). Complete manual check: `gh workflow run ci.yml -f full=true` on main (also the Flatpak build and the Windows build and installer test); release builds are separate and never use a cache.
**Caching.** `actions/cache` (pinned) in `ci.yml` and in `windows.yml` for development runs only: key = system, exact `rustc --version`, all lockfiles, `.cargo/config.toml`, the workflow file (the restore key widens it to the same system and compiler); cargo rebuilds what differs and a checkout makes the workspace crates new. Caches are scoped by GitHub to the branch and to main. The Windows cache is opt-in: `windows.yml` has the boolean `workflow_call` input `use_cache` (default false); `ci.yml` passes `true`, `release-set.yml` passes `false` explicitly, and a manual run of `windows.yml` itself restores it (`github.event_name == 'workflow_dispatch'` and `github.workflow == 'windows'`); policy tests check all of this, and no release workflow may use `actions/cache`. A called workflow receives no secret and no write permission (checked too). In `ci.yml` an optional part is skipped only on an explicit `false` of the decision step (fail-safe: a broken step means everything runs). Development test builds use `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=0` (smaller caches; installers and Flatpak are `--release`). Billing facts used: Windows job minutes count double; job minutes are rounded up; the measured use between 2 and 16 November was 1817 billed minutes (`ci` 338, `flatpak` 411, `windows` 466, release rehearsals 602).

Policy tests enforce main/ref guards, ancestor checks, version consistency, read-only RC permissions, no publication and pinned action SHAs. RC builds may be selected manually from `main` or an existing version tag; tags must equal `v` + `APP_VERSION` and point to a commit on `main`. Agents never create tags.

The private workflows remain available for owner-directed development validation. Agents do not push, tag, dispatch any workflow or publish. The public repository has a separate `.github/workflows/release.yml`: an owner-pushed numeric version tag triggers its build, validation and GitHub release. Ordinary commits do not trigger a public release. Do not copy the private workflow files into the public repository as a substitute.

RC steps: checks and tests → measured cleanup of Rust test targets → vendoring and Flatpak build/bundle → measured cleanup of Flatpak build state and SDK → stage the source archive twice and compare SHA-256 → unpack and run `version.py check` and pinned Rust 1.99.0 `cargo check --locked --offline` for both launcher crates using vendored dependencies → measured cleanup of source-check targets → assemble exactly the Flatpak, source archive and `SHA256SUMS` → release-set validation → install bundle and check CLI version → audit source and installed Flatpak for prohibited content → upload private workflow artifacts (30 days). Nine disk measurements retain evidence of resource use. The job limit is 120 minutes.

Checks establish build and artifact properties, not game compatibility. The owner confirmed installation, game start, multiplayer and resolution persistence on one Steam Machine with private builds. This does not prove broad GPU or distribution compatibility for public `0.2.0`. The manifest uses Freedesktop 25.08, `--allow=multiarch`, and the `Compat.i386` and `GL32` extension points following the Steam Flatpak pattern. The only host folder shared is `~/Games/The Secret World`.

### Public release assets
The public tag workflow `release.yml` is the pipeline of section 5: it validates the tag, the version and the sources, takes the Flatpak bundle, the source archive and the Windows installer that `build.yml` built and checked for exactly this commit when it was pushed to `main` (it compiles nothing), and, after the two human approvals, publishes exactly four files as the GitHub release: `tsw-forever-<version>.flatpak`, `tsw-forever-<version>-src.tar.gz`, `tsw-forever-<version>-windows-setup.exe` and `SHA256SUMS`. The web site finds these files at run time through the GitHub API; it needs no change per release.

## 5. Release pipeline (`release.yml`) and the web site
GitHub Pages carries the **static web site only** (public repository only). The release files are assets of the GitHub release; the web site's download buttons find them at run time (`website/js/download.js`: GitHub API `releases/latest`, which never returns a draft or a pre-release; only exact file names of the same version and repository addresses are accepted). Nothing of a release is ever put on Pages, so the Pages artifact is small (a few hundred kilobytes) and independent of any release; `scripts/assemble_pages_site.py` refuses an installation or repository file inside it.

**Build on push (`build.yml`).** A push to `main` builds and tests the candidate (Flatpak bundle, source archive, Windows installer), writes `candidate.json` and deploys the web site (job `site`: web site tests, assembly, tip-of-`main` check, deployment; it does not wait for the builds). It creates no release and no tag.

**Release on tag (`release.yml`).** The owner pushes `vMAJOR.MINOR.PATCH` on a commit of `main` whose `build` run succeeded. Everything else is GitHub Actions, with two human approvals that GitHub enforces (environments with required reviewers):

1. `guard` (tag, `main`, version, newer than the newest published release, pinned actions) and `candidate` (the successful `build` run of exactly that commit, every file checked against `candidate.json`, nothing compiled).
2. **Approval 1** (environment `flatpak-release`, now the approval of the whole release, Linux and Windows together): job `approve`. Nothing is put into a draft before it.
3. `draft` assembles the four release files, checks the set and the checksums and fills a DRAFT release, read back and compared.
4. **Approval 2** (environment `release-publish`): `publish` verifies the draft once more and publishes it.

There are no GPG keys, no signing and no secrets any more (the signed OSTree repository of the unpublished 0.4.0 was dropped; `security.md` section 3 states what protects the files instead). The environments' settings are the owner's and are not changed by any workflow or agent; secrets that remain in `flatpak-release` from the 0.4.0 plan are unused and can be removed by the owner. Details, recovery and the owner's command sequence: `release-pipeline.md`.

### Signing keys
Private keys are generated on the owner's machine, outside the repository (for example `~/.local/share/tsw-forever-keys/`, mode `700`, backed up offline). `.gitignore` also blocks key file patterns. Only public keys go into the code. No production key exists yet; nothing in the repository creates one by itself.
* **minisign** (client-patch manifests, and later the launcher update metadata of the stable channel): `minisign -G -p patch.pub -s patch.key`; put the Base64 line of `patch.pub` into `PATCH_PUBLIC_KEY` in `launcher/src/project.rs` (this activates the patch system). Sign patch releases locally with `scripts/make_patch_release.sh … --key patch.key` (never in CI, the old files are original game files and must not leave the maintainer's machine). The launcher accepts only prehashed `ED` signatures. The key is compiled in, so rotation needs a new launcher release. The update-metadata key is separate (`UPDATE_PUBLIC_KEY` in `packaging/channels/stable.conf`, empty until generated); its private half stays outside CI.
* **GPG:** not used any more. The Flatpak bundle of 0.4.1 is not signed and no OSTree repository is hosted (`security.md` section 3). The former production keys and the key scripts were removed from the repository; the owner keeps the keys offline and may delete them.

## 5a. Flatpak bundle: install, update, downgrade
The bundle is a plain single file (`flatpak build-bundle`, no `--repo-url`, no `--gpg-keys`), branch `local` (the branch of the earlier bundles, so that an installed version is updated in place), installed with `flatpak install --user <file>.flatpak`. Releases and developer builds share that branch; a release is told from a developer build by build metadata: `TSW_RELEASE_BUILD=1 scripts/build_flatpak.sh build|bundle` puts `packaging/release-build` into the staged tree (never into Git: `.gitignore`), `launcher/build.rs` sets `cfg(release_build)`, and the programs then contain the marker string `tsw-forever-release-build`, which `flatpak-stable-build.yml` checks in the installed bundle and `rc-artifacts.yml` checks to be ABSENT in development bundles. `scripts/e2e_flatpak_bundle.sh` (also in `ci.yml`) proves with the real Flatpak and a stand-in application in a throw-away installation: a fresh install works and creates the branch `local` (B1); a newer bundle installed over the old one is an update and the user's data in `~/.var/app/<id>` stays byte-identical (B2, B3); the same bundle again is refused and an OLDER bundle is installed without a warning (B4, the reason why the documentation names the newer bundle only); the bundle configures no remote with an address (B5); after the update exactly one branch (`local`) exists, so an installation of 0.3.0 or older is updated in place without any migration (B2). `--bundle <file>` additionally installs a real bundle into the throw-away installation and inspects it (never runs it). The CI job that builds the bundle installs it once for real, starts `tsw-launch --version` and runs the content audits.

## 5b. Windows update metadata (offline-signed) - DEVELOPMENT ONLY, not part of any release
Product decision (2026-11): Windows has no automatic update, so **no release carries `update-stable.txt` or its signature** and nothing in the release process creates them. This section is kept for the development feature `windows-self-update` (see `building-windows.md`). The Windows launcher update (`building-windows.md`) reads `update-stable.txt` and `update-stable.txt.minisig` from the latest stable release. After the release set exists: `scripts/make_update_metadata.py --version <v> --installer tsw-forever-<v>-windows-setup.exe [--previous-version <p> --previous-installer tsw-forever-<p>-windows-setup.exe]` writes the unsigned metadata (size and SHA-256 of the installers, addresses of the official release, validity at most 400 days, default 180); sign it OFFLINE with the owner's minisign key (`minisign -S -s <key> -m update-stable.txt`); attach both files to the release. The metadata is re-issued for every release (the launcher refuses expired metadata), and a previous version makes the recovery possible. The private key is never in CI.

## 6. Licence of the build
The project is GPL-3.0-or-later. The GUI uses Slint under its GPL-3.0 option; anyone distributing the binaries must offer the complete source including build scripts, which is why a public repository (or a written source offer) is required for a public release. Third-party Rust libraries and their licences are listed in `THIRD-PARTY-NOTICES.md`.

## Hardening and public preparation

The owner has published public `0.2.0` after private Steam Machine testing. The Microsoft EU/German assessment and integrated original-term consent are documented in `microsoft-components.md`; remaining interpretation questions are still disclosed and require renewed review if circumstances change. The existing private releases remain unchanged.

Flatpak binaries install `LICENSE`, `THIRD-PARTY-NOTICES.md`, the complete `LICENSES` inventory/materials and the GUI lockfile under `/app/share/licenses/tsw-forever/`. The source archive carries the same materials. `scripts/check_licenses.py` verifies source checksums, selected Linux dependencies and every required text; the RC audit checks the installed payload as well. Own code remains GPL-3.0-or-later; the combined GUI and AppStream distribution licence are GPL-3.0-only because that is the selected Slint licence.

There is no automatic GitHub bundle updater. See the public `README.md` for manual installation of a newer bundle, retained data and uninstallation. Later public source snapshots must pass the `check_public_source.py` audit, contain the corresponding editable sources/build information, and omit private history and branding (`public-export.md`).
