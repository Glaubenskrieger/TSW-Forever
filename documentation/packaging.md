# Packaging, CI and releases

How TSW-Forever is built, packaged and released. Release rules (versions, tags, channels) are in `versioning-policy.md`; trust and secrets in `security.md`; third-party components in `third-party-components.md`.

## 1. Formats
| Format | Build | Notes |
|---|---|---|
| Flatpak `org.tswlauncher.Launcher` | `scripts/build_flatpak.sh` | official Linux binary format; not published on Flathub |
| Source archive | `scripts/native_stage.sh` | deterministic `tsw-forever-<version>-src.tar.gz`; Git source is also available |

There are no distribution-specific Linux packages. The native Windows build has its own per-user installer (`packaging/windows/`, Inno Setup; see `building-windows.md`); it is a separate operating system, not a Linux distribution package. No artifact contains game data, Funcom or Microsoft files, or a Wine/Proton runner. The Flatpak app ID must remain unchanged to preserve update identity.

## 2. Flatpak
* Runtime Freedesktop 25.08, SDK extension `rust-stable`, 32-bit support through `--allow=multiarch` (the game client is a 32-bit program). Programs: `/app/bin/tsw-launcher` (GUI) and `/app/bin/tsw-launch` (CLI, in the same folder so the GUI finds it).
* **Sandbox permissions** (`finish-args`, each one needed): `--socket=x11`, `--socket=wayland` (GUI, and Wine through XWayland), `--device=dri` (GPU), `--socket=pulseaudio` (audio), `--share=network` (game servers, downloads, update check), `--share=ipc` (X11 shared memory), `--allow=multiarch`, and exactly one folder: `--filesystem=~/Games/The Secret World:create`. No home, no `~/Games` as a whole, no Steam folder, no `--device=all`, no system or session bus, no `flatpak-spawn --host`. `scripts/check_flatpak_package.py` rejects anything else.
* **Data:** everything managed lives in `~/Games/The Secret World/{prefix,runtime,downloads,cache,logs}`; settings in `~/.var/app/org.tswlauncher.Launcher/config/tsw-launch/`. A Flatpak update only replaces `/app`. `flatpak uninstall --delete-data` removes the app data directory but not `~/Games/The Secret World`.
* **Wine/Proton:** not in the package. The launcher downloads a pinned GE-Proton archive (SHA-256 and size compiled in, https from GitHub) after explicit consent, verifies it before unpacking (only the expected root folder, no `..` or absolute paths) and installs it atomically into `<base>/runtime`. An existing runtime is never replaced.
* **Update check and update:** a stable Flatpak asks the host's update portal (`org.freedesktop.portal.Flatpak`, `CreateUpdateMonitor`) and listens for `UpdateAvailable`; the window offers the update, and only after the user agrees it calls `Update`, which the host's Flatpak performs (GPG-checked, atomic, delta where available). The running program is not changed; the new version starts the next time. The first update may trigger a system question (permission `flatpak/updates`); the user can allow it permanently or deny it. No sandbox permission is added and nothing is written into `/app`. Packages without an update source (branch `local`, testing packages) show nothing. Offline, without a portal or without a published repository the window is silent and unchanged. The plain hint with `flatpak update org.tswlauncher.Launcher` remains only as a fallback for a Flatpak without the portal.
* **Build:** `scripts/build_flatpak.sh` has the steps `stage`, `fetch`, `vendor`, `test`, `check`, `build`, `bundle` (offline after `fetch`/`vendor`). Fixed inputs: runner `ubuntu-24.04`, Freedesktop 25.08, `Cargo.lock` with `--locked`, vendored crates, `SOURCE_DATE_EPOCH`. Not fixed: apt package state on the runner and the Flathub state of the runtime branch.

## 3. Source archive
`scripts/native_stage.sh` selects the three Rust crates, lockfiles, UI, translations, icons, licences, install script and build instructions. It normalises entry order, owner, timestamps, modes and locale and uses `gzip -n`. No vendored libraries are included. See [`building-from-source.md`](building-from-source.md) for dependencies, building, offline vendoring and installation with `scripts/install_native.sh`.

A source build uses the host's 32-bit Wine dependencies and Vulkan drivers; `tsw-launch doctor` reports missing libraries. External tools include `curl`, `tar`, `gzip`, `bsdtar`, `cp`, `sh` and optionally `gamescope`. The source-built programs run outside the Flatpak sandbox.

## 4. CI workflows (`.github/workflows/`)
| Workflow | Trigger | Does | Must not |
|---|---|---|---|
| `ci.yml` | every push and pull request, manual (`full`) | format, Clippy (`-D warnings`), Rust and policy tests, tests of the development feature `windows-self-update` (same target folder), the Flatpak update end-to-end test (`scripts/e2e_flatpak_update.sh`, only when Flatpak, signing, script, workflow or Rust files changed), secret scan, prepublication and static Flatpak checks; on main it then CALLS `flatpak.yml` (`needs: checks`), and a manual run with `full` also calls `windows.yml` | publish, use secrets, build a package outside main or before its own checks passed |
| `flatpak.yml` | called by `ci.yml` on main after all checks are green (`tests-passed`), or manual (then with its own tests) | checks, vendoring, Flatpak build and bundle artifact | publish, use secrets, build other refs, be started by a push itself |
| `rc-artifacts.yml` | manual only | Flatpak and source archive, reproducibility, offline source compilation check, installed-bundle version and content audits | create releases, push, tag, use secrets or write permissions |
| `build.yml` | every push to `main`; manual on `main` or an existing tag | BUILD ON PUSH: calls `flatpak-stable-build.yml` and `windows.yml`, writes `candidate.json` (SHA-256 of every artifact, kept 30 days) and deploys the web site (published Flatpak data carried over unchanged) | sign, create a release or tag, activate a Flatpak update, use secrets or environments |
| `release.yml` | an owner-pushed tag `vMAJOR.MINOR.PATCH` only (no manual start, no other trigger) | RELEASE ON TAG (section 5, `release-pipeline.md`): verifies the candidate of the build run of exactly that commit (compiles nothing), signs (environment `flatpak-release`), fills a draft, deploys Pages, checks the live source, publishes (environment `release-publish`) | publish without both approvals, hold the key outside the job `sign`, touch a published release, create tags |
| `flatpak-stable-build.yml` | called by `build.yml` and `release-dry-run.yml` | tests, UNSIGNED stable OSTree repository, source archive | sign, publish, use secrets, environments or write permissions |
| `release-dry-run.yml` | manual only, `main`, no input | rehearsal of the pipeline with a throw-away key made inside the job | use secrets or environments, deploy, tag or publish |

**CI structure and cost rules (since 2026-11-16).** One run per commit owns the tests; nothing is tested twice: `ci.yml` runs every check, then on main (for changes that can reach the package: Rust crates, `packaging/`, `scripts/`, `.cargo/`, workflows) its job `flatpak` calls `flatpak.yml` with `needs: checks`, so the expensive package build starts only after every check of the same commit is green and the build workflow skips its own test step (`tests-passed`; a manual run of `flatpak.yml` still runs them). A reusable test workflow or a query for an earlier successful run were considered and rejected: `workflow_run` triggers are forbidden by the policy test, `needs` cannot cross workflows, and waiting for another run costs billed minutes. Optional parts are skipped only when nothing of their area changed (the "Decide" step of `ci.yml`: documentation-only changes skip the Rust feature tests; the end-to-end test needs Flatpak, signing, script, workflow or Rust changes; a new branch, an unknown or rewritten history range and a manual `full` run do everything; always run: version/pin check, formatting, Clippy, the Rust and Python tests including the i18n completeness tests, the secrets and prepublication scans, the policy checks and the static Flatpak validation). Complete manual check: `gh workflow run ci.yml -f full=true` on main (also the Flatpak build and the Windows build and installer test); release builds are separate and never use a cache.
**Caching.** `actions/cache` (pinned) in `ci.yml` and in `windows.yml` for development runs only: key = system, exact `rustc --version`, all lockfiles, `.cargo/config.toml`, the workflow file (the restore key widens it to the same system and compiler); cargo rebuilds what differs and a checkout makes the workspace crates new. Caches are scoped by GitHub to the branch and to main. The Windows cache is opt-in: `windows.yml` has the boolean `workflow_call` input `use_cache` (default false); `ci.yml` passes `true`, `release-set.yml` passes `false` explicitly, and a manual run of `windows.yml` itself restores it (`github.event_name == 'workflow_dispatch'` and `github.workflow == 'windows'`); policy tests check all of this, and no release workflow may use `actions/cache`. A called workflow receives no secret and no write permission (checked too). In `ci.yml` an optional part is skipped only on an explicit `false` of the decision step (fail-safe: a broken step means everything runs). Development test builds use `CARGO_INCREMENTAL=0` and `CARGO_PROFILE_DEV_DEBUG=0` (smaller caches; installers and Flatpak are `--release`). Billing facts used: Windows job minutes count double; job minutes are rounded up; the measured use between 2 and 16 November was 1817 billed minutes (`ci` 338, `flatpak` 411, `windows` 466, release rehearsals 602).

Policy tests enforce main/ref guards, ancestor checks, version consistency, read-only RC permissions, no publication and pinned action SHAs. RC builds may be selected manually from `main` or an existing version tag; tags must equal `v` + `APP_VERSION` and point to a commit on `main`. Agents never create tags.

The private workflows remain available for owner-directed development validation. Agents do not push, tag, dispatch any workflow or publish. The public repository has a separate `.github/workflows/release.yml`: an owner-pushed numeric version tag triggers its build, validation and GitHub release. Ordinary commits do not trigger a public release. Do not copy the private workflow files into the public repository as a substitute.

RC steps: checks and tests → measured cleanup of Rust test targets → vendoring and Flatpak build/bundle → measured cleanup of Flatpak build state and SDK → stage the source archive twice and compare SHA-256 → unpack and run `version.py check` and pinned Rust 1.99.0 `cargo check --locked --offline` for both launcher crates using vendored dependencies → measured cleanup of source-check targets → assemble exactly the Flatpak, source archive and `SHA256SUMS` → release-set validation → install bundle and check CLI version → audit source and installed Flatpak for prohibited content → upload private workflow artifacts (30 days). Nine disk measurements retain evidence of resource use. The job limit is 120 minutes.

Checks establish build and artifact properties, not game compatibility. The owner confirmed installation, game start, multiplayer and resolution persistence on one Steam Machine with private builds. This does not prove broad GPU or distribution compatibility for public `0.2.0`. The manifest uses Freedesktop 25.08, `--allow=multiarch`, and the `Compat.i386` and `GL32` extension points following the Steam Flatpak pattern. The only host folder shared is `~/Games/The Secret World`.

### Public release assets
The public tag workflow `release.yml` is the pipeline of section 5: it validates the tag, version and sources, takes the Flatpak repository, the source archive and the Windows installer that `build.yml` built and checked for exactly this commit when it was pushed to `main` (nothing is compiled at the tag), signs the Flatpak repository in one protected job, attaches exactly four files (`tsw-forever-<version>.flatpak`, `-src.tar.gz`, `-windows-setup.exe`, `SHA256SUMS`) to a DRAFT release, deploys the update source and the web site to GitHub Pages, checks that they are reachable and verify, and publishes the draft only after the owner's second approval. It accepts only owner-pushed tags of the form `vMAJOR.MINOR.PATCH`. The private RC-artifact process above is historical/private validation. Existing private RC assets and tags remain unchanged.

## 5. Release pipeline and publishing the Flatpak repository (`release.yml`)
Hosting through GitHub Pages (public repository only: Pages for a private repository needs a paid plan and its site would be public anyway). Everything from the tag to the published release runs in GitHub Actions, with two human approvals that GitHub enforces through environments:

1. `guard`, then the builds `flatpak` (UNSIGNED stable repository, source archive) and `windows` run first, on machines that hold no key.
2. **Approval 1** (environment `flatpak-release`): only then the signing SUBKEY of the project key is released to the job `sign`. `scripts/flatpak_sign_ci.sh` signs commits and summary, generates the static deltas afterwards, verifies against the committed public key `packaging/flatpak/stable-repo.gpg` and proves the update over the signed deltas. The PRIMARY key never leaves the owner's offline storage; only a signing subkey is in GitHub (secret `TSW_FLATPAK_SIGNING_KEY`, variable `TSW_FLATPAK_SIGNING_FINGERPRINT` of the environment). The job runs only repository scripts and distribution packages; nothing is compiled in it.
3. `verify-signed` builds the signed stable bundle (it carries the update source and the public key) and checks that it is the bundle of the signed repository; `draft` puts the four release files into a draft and reads them back.
4. `pages-build` and `deploy` publish the web site, the signed repository, `tsw-forever.flatpakrepo` and `org.tswlauncher.Launcher.flatpakref` together; `verify-live` checks that every file is reachable and that the live repository verifies like a user's Flatpak (`scripts/check_flatpak_live.sh`).
5. **Approval 2** (environment `release-publish`): the job `publish` verifies the draft once more and publishes it. The Flatpak update source is already public after step 4; the approval gates the release page.

**The public repository carries stable only**: `scripts/flatpak_channel.py` enforces final versions, strictly newer than the live site; no testing branch, ref or install file ever exists there (testing packages are a separate application with a separate application ID, handed out by hand from private CI artifacts). A failed job is re-run on its own; a failure before `deploy` leaves nothing public. A rehearsal with a throw-away key is `release-dry-run.yml`.

**Site layout.** A Pages deployment replaces the whole site, so the web site and the repository are always assembled together: `/repo/` (OSTree, served as static files), `/tsw-forever.flatpakrepo`, `/org.tswlauncher.Launcher.flatpakref`, `/channels.json`, `/.nojekyll`, and the web site sources from the Git repository (a `website/` folder, optional) for everything else; the names above are reserved and the assembler refuses a web site that uses them. The earlier commits of the repository are mirrored from the live site before the new one is added, so the new commit has the previous one as parent, static deltas are generated (previous to new) and old users download the difference only. Pages limits: site at most 1 GB, soft limits of 100 GB bandwidth per month; the repository keeps two commits (`--prune-depth=2`).

**One-time setup by the owner:** provide the existing keys (export of the signing subkey only; public key file `packaging/flatpak/stable-repo.gpg`); environments `flatpak-release` (secret, variable, reviewer, tag pattern), `release-publish` (reviewer, tag pattern) and the tag pattern for `github-pages`; Pages source "GitHub Actions"; a tag ruleset for `v*`. None of this is part of the repository; the owner does it personally.

### Signing keys
Private keys are generated on the owner's machine, outside the repository (for example `~/.local/share/tsw-forever-keys/`, mode `700`, backed up offline). `.gitignore` also blocks key file patterns. Only public keys go into the code. No production key exists yet; nothing in the repository creates one by itself.
* **minisign** (client-patch manifests, and later the launcher update metadata of the stable channel): `minisign -G -p patch.pub -s patch.key`; put the Base64 line of `patch.pub` into `PATCH_PUBLIC_KEY` in `launcher/src/project.rs` (this activates the patch system). Sign patch releases locally with `scripts/make_patch_release.sh … --key patch.key` (never in CI, the old files are original game files and must not leave the maintainer's machine). The launcher accepts only prehashed `ED` signatures. The key is compiled in, so rotation needs a new launcher release. The update-metadata key is separate (`UPDATE_PUBLIC_KEY` in `packaging/channels/stable.conf`, empty until generated); its private half stays outside CI.
* **GPG** (stable Flatpak repository). The production keys already exist and are never created by this repository: a certify-only PRIMARY key (RSA 4096, no expiry, fingerprint `FAF3884F3E41D5C63FE656DC86075D3D53A6484B`, kept by the owner for good together with its backups and revocation certificate) and a separate signing SUBKEY (RSA 4096, sign only, no expiry, key id `43F56AAA62FBF7DA`, protected by a passphrase). Both values are pinned in `packaging/project.conf`; `packaging/flatpak/stable-repo.gpg` (public parts only, provided by the owner) must hold exactly this key (`scripts/flatpak_keys.sh check-pin`). Only the subkey is in GitHub: the environment `flatpak-release` holds the secrets `TSW_FLATPAK_SIGNING_KEY` (the subkey, base64 on one line, the primary secret key only a stub; checked before the upload with `flatpak_keys.sh inspect-ci-export`) and `TSW_FLATPAK_SIGNING_PASSPHRASE` and the variables `TSW_FLATPAK_SIGNING_FINGERPRINT` and `TSW_FLATPAK_SIGNING_SUBKEY_ID`. The release pipeline signs with that subkey (`scripts/flatpak_sign_ci.sh`) and never needs the primary key. Per release nothing is done by hand: the pipeline mirrors the live stable branch (so the new commit has the previous one as parent and static deltas are made), builds the UNSIGNED repository, signs, verifies, bundles and publishes as described above. The other commands of `scripts/flatpak_keys.sh` that create or export keys are for automated tests with throw-away keys. `scripts/flatpak_release_offline.sh` remains as a tool for tests and emergencies only and is never part of a release. Details: `documentation/release-pipeline.md`.
  A stable bundle must be built from a signed repository: installing it enables signature checking, so a bundle from an unsigned repository cannot be installed (verified), and `bundle` refuses it. Rotation: publish a new public key in a new launcher release (bundles carry the key) and keep the old key valid until users have updated; a Flatpak client stores the public key once and never refreshes it, so the production keys have no expiry; protection comes from revocation with the primary key (kept by the owner) and from rotation. Revocation of a key makes new commits unverifiable. Never put the PRIMARY key, a keyring or any export of the primary key into the repository, a workflow, a secret or a log; the only secret in GitHub is the signing subkey in the environment `flatpak-release`.

## 5a. What actually triggers a Flatpak update (research notes, M5)
A signed repository only makes an update available; **Flatpak itself has no background updater**: nothing runs `flatpak update` unless something asks it to. These notes come from the documented behaviour of the components and are not yet confirmed on the target systems (the M5 test plan does that, on the owner's Linux machine and a SteamOS device); treat every line as a hypothesis until it is ticked there.
* **Our launcher (the reliable trigger, no extra infrastructure):** while the launcher runs it asks the Flatpak update portal (`CreateUpdateMonitor` / `Update`, see `launcher/src/update/flatpak.rs`); the host's Flatpak does the download, signature check and installation after the user agrees. This works on every distribution that ships the portal, independent of any software centre, and was verified once against a real portal (M3). Limit: it only happens when the launcher is started.
* **Software centres** (GNOME Software, KDE Discover, and the centres of distributions such as Fedora, Bazzite or Endless OS) check installed Flatpak refs on their own schedule and offer or install updates according to their settings. They need the project's remote to be configured as a normal remote (it is, by the bundle and by the `.flatpakrepo` file) and the remote's AppStream data for names and icons; `flatpak build-update-repo` generates that data from the exported metainfo. Defaults differ (notify only, download only, install automatically), so no automatic installation can be promised.
* **SteamOS:** system updates are Valve's; Flatpak applications are updated from Desktop Mode through Discover or `flatpak update`. Game Mode is not known to update Flatpaks. Whether SteamOS updates third-party remotes unattended is to be confirmed on a device. Consequence for the documentation: promise "the launcher offers the update when it starts" and "your software centre or `flatpak update` also works", not a silent background update.
* **Optional recipe, never installed by us:** a user-level systemd timer that runs `flatpak update --user -y org.tswlauncher.Launcher` gives unattended updates without our involvement. It is persistent configuration on the user's machine, so it is documented only as a manual recipe if at all, and the launcher never creates it.

## 5a2. End-to-end test of the update chain (`scripts/e2e_flatpak_update.sh`)
Runs on Linux (flatpak, ostree, gpg, python3, curl) and in `ci.yml`; `scripts/e2e_flatpak_update.sh [--keep]`. Run `scripts/e2e_flatpak_update.sh --self-check` first: it only checks the isolation (see below) and installs nothing. It uses **temporary keys** (new throw-away GNUPGHOMEs, deleted at the end), a **local repository** served on 127.0.0.1, a **throw-away Flatpak user installation** (`FLATPAK_USER_DIR`) and a tiny test application with its own ID; it needs no network, publishes nothing and creates or reads no production key. Flatpak and OSTree do the verification; the script drives them and our own signing path (`flatpak_keys.sh sign-repo` / `verify-repo`).
* S0 our verification tool accepts a repository signed with the right key and refuses an unsigned one and one for another key. S1 install from the signed repository. S2 update (signed, static deltas).
* S3 refused, installed version stays: an unsigned new version, one signed with a foreign key, one with a corrupted object.
* S4 rollback: a replayed OLD signed repository state must not be taken as an update (this depends on Flatpak's own downgrade protection and is reported as a note, a failure only with `E2E_STRICT_ROLLBACK=1`; see the result on the target systems); the **authorised restore** of the previous version works (`flatpak update --commit=<commit of the previous version> <app>`, possible while the repository still carries that commit: releases are pruned to depth 2, i.e. the previous version only) and the next normal update leads back to the newest version.
* S5 key rotation and revocation with keys A (old) and B (new): a version signed with both keys is accepted by clients that know only A; after the client has received B a B-only version is accepted; a client that never received B refuses it (the rotation therefore needs a dual-signed period and a release/key file that delivers B first); after a revocation (the client is set up again with B only, what a new bundle does) a release signed only with the compromised key A is refused.
**Static deltas must be generated AFTER the signing (`scripts/check_flatpak_delta_update.sh`).** A static delta carries its own copy of the commit and of its signature (inside the delta's `superblock`). A delta that was generated before the commit was signed has no signature in it, and a client that takes the delta path (every normal update does) stops with `GPG verification enabled, but no signatures found`, although the commit and the summary are signed correctly and `flatpak_keys.sh verify-repo` is green (it checks the refs and the summary, not the deltas). This was found when a signed test update failed at 0 %: the throw-away test repository had run `flatpak build-update-repo --generate-static-deltas` before the signing, and `sign-repo` does not regenerate deltas that already exist. The same happens with `flatpak build-commit-from`, which generates the delta from scratch to the new commit at the moment it creates the still unsigned commit (the throw-away test repositories of the launcher-update test make their second release with it, and now remove the deltas of the new commit before signing, so that `sign-repo` makes them again, signed). The release order is right: `flatpak_keys.sh sign-repo` runs `flatpak build-sign` first and generates the deltas afterwards (S2 above covers it with a real client). `scripts/check_flatpak_delta_update.sh [--require-delta] [--extra-key <public-key.gpg>]... <repository> <public-key.gpg> [ref ...]` proves it for a given repository: it serves the repository from a throw-away local http server, lets a fresh scratch repository that trusts only the given key (`gpg-verify` and `gpg-verify-summary` on) read the summary, and then, for EVERY static delta that targets the newest commit of a ref (from scratch and from each older commit), pulls over HTTP and requires success, delta parts in the result (not the object fallback) and a requested delta superblock. A missing or wrong signature, an unsigned summary, another key and (with `--require-delta`) a ref without any delta make it fail (exit 1); a wrong call or a missing tool is exit 2. It only reads the repository. The older commits (the history the update starts from) must be verifiable with the given key too, so nothing older is trusted silently: after a KEY ROTATION (history signed with the previous key, the new release with the new one) the check fails until the previous public key is named explicitly with `--extra-key` (repeatable). An extra key is trusted for the older commits of the delta tests only; the summary and the newest commit are always verified with the given key alone, every extra key is printed with a WARNING and its fingerprint, and a file that holds a secret key is refused. **The release flow runs this check** (`flatpak_release_offline.sh`, after `verify-repo` and before the bundle is built, with this release's public key and `--require-delta`): a failure stops the release with exit 21 and nothing is bundled. For the one release that rotates the key, name the previous public key file(s) deliberately: `FLATPAK_RELEASE_EXTRA_TRUSTED_KEYS=/path/to/previous-public-key.gpg scripts/flatpak_release_offline.sh ...` (colon-separated for several; the files are checked before the build starts); without it the check refuses an older commit that only a previous key has signed. The same variable is read by the mirror of the live history (next paragraph), so under a rotation the previous key names both what may be mirrored and what the check accepts as older history; a dual-signed history (see the rotation concept above) verifies with the new key alone and needs no extra key. `scripts/test_check_flatpak_delta_update.py` (part of `build_flatpak.sh test`) rebuilds the failure class with the real tools: the release order passes, deltas before the signing fail while `verify-repo` stays green, and an unsigned repository, another key, a release without deltas, a key rotation without the explicit previous key and an extra key that would vouch for the new state fail. **Mirroring the live history (`scripts/flatpak_mirror_live.sh`, used by `build_flatpak.sh stable-repo`).** When a live repository is configured (`FLATPAK_LIVE_REPO_URL`, the release script's `--live-url`) its stable branch is mirrored first, so that the new commit gets the previous release as its parent and the static deltas previous -> new exist. A live repository that was GIVEN must be mirrored: if that fails (unreachable, 404, an unsigned or wrongly signed summary or commit, a key that is not trusted) `stable-repo` stops with the exit code of the mirror (19; 18 for a key problem) and no release is built, because it would otherwise go out silently without its history. Told apart by exit code and by a `MIRROR:` line: **mirrored** (0, the history is taken over); **first release** (3, nothing to take over: no live URL configured, or the live repository was read with a verified summary and has no stable branch yet); **failed** (19). A real first release gives no live URL; a 404 for a URL that was given is a failure, not a first release. The summary and every mirrored commit are verified (`gpg-verify` and `gpg-verify-summary` on, never off) against this release's public key and the previous public keys named in `FLATPAK_RELEASE_EXTRA_TRUSTED_KEYS` (colon-separated, public keys only, a secret key file is refused with exit 18); those previous keys vouch for the OLD history only, the new commit is signed afterwards with this release's key, and `verify-repo` and the delta check accept it with that key alone. After a rotation without the previous key named the mirror fails with a message that says so. `scripts/test_flatpak_mirror_live.py` (part of `build_flatpak.sh test`) tests the script against real repositories served over a local http server (first release, successful mirror, rotation with and without the previous key, an extra old key that does not confirm a new commit, missing, secret and empty key files, an unsigned repository, another key, a closed port, 404, wrong calls) and runs the REAL `cmd_stable_repo` of `build_flatpak.sh` (dispatcher cut off, `flatpak-builder` a stub) to prove that a failed mirror builds nothing. The mirror script is a tool of the release owner like `flatpak_keys.sh` and is not part of the source archive; `stable-repo` without a live URL does not need it.
**These tests must run in CI, not be skipped.** The tests of the signing (`test_flatpak_keys.py`), the delta update (`test_check_flatpak_delta_update.py`), the mirror (`test_flatpak_mirror_live.py`) and the release script (`test_flatpak_release_offline.py`) need `flatpak`, `ostree`, `gpg` (and `git`, `tar`, `sha256sum`, `timeout`). On a developer machine without them a test class is skipped, but in every CI job that runs `scripts/build_flatpak.sh test` (`ci.yml` job `checks`, `flatpak.yml`, `rc-artifacts.yml`) the environment variable `TSW_REQUIRE_TOOLS=1` is set and the packages `flatpak ostree gnupg` (plus `curl` for the end-to-end test) are installed by an EARLIER step of the same job: a missing program is then a failure, never a silent skip (`scripts/testtools.py` for the test classes, and a preflight at the start of `build_flatpak.sh test` that stops with exit 10 and the reason). This closes a gap in which the Flatpak tools were installed only after the tests, so 38 of these tests passed without running. `scripts/check_flatpak_package.py ci-policy` enforces it for every workflow (the variable, and the packages installed before the step); `scripts/test_check_flatpak_package.py` mutates the shipped workflows to prove that, and `scripts/test_testtools.py` tests the helper, the preflight and that program-dependent tests use the helper. Skips that stay are about the state, not a missing program: no local release set (`test_check_release_*`), no built repository (`test_check_flatpak_package.py`), no copy of the game client (`test_fps_cache_cli.sh`).
`scripts/test_flatpak_release_offline.py` (also part of `build_flatpak.sh test`) runs the REAL release script, `flatpak_keys.sh` and the check in a temporary tree with a stub in place of the Flatpak build: a release with signed deltas (and a first release without history) is bundled, an intentionally invalid delta path and a key rotation without the previous key stop the release with exit 21 before anything is bundled, a rotation with the previous key named is accepted with a warning, a missing key file stops it before the build, and the call is verified to sit between `verify-repo` and the bundle.
Isolation: every Flatpak call runs with `HOME`, the XDG folders, `FLATPAK_USER_DIR`, `FLATPAK_SYSTEM_DIR`, `FLATPAK_CONFIG_DIR` and `GNUPGHOME` pointing into one temporary folder, and each test client is a `--user` command of its own throw-away installation, so the real user and system installations, their remotes and `~/.gnupg` are not reached (no `sudo`, no polkit). The real installations are only listed (read-only) before and after and compared; a difference is a failure. At the end, also after an error, Ctrl-C or SIGTERM, the local server and the per-keyring gpg-agents are stopped and the temporary folder (keys, repositories, installations) is deleted; only SIGKILL or a power loss can leave `/tmp/tsw-e2e-XXXXXX`, which holds nothing but temporary test data. On SteamOS the root file system is not touched (everything is below `/tmp`); the `ostree` command-line tool must exist (it is a dependency of the `flatpak` package on Arch, to be confirmed on the device; the script exits with code 10 and a message if a tool is missing, and nothing is installed for it).
Authorised restore versus unauthorised rollback: a restore is a deliberate, local action by the user (`--commit`, documented in the user guide) and only reaches commits that carry our valid signature; a rollback imposed from outside is a served older state, which only works if someone controls the repository (GitHub Pages of the project) or defeats the client's downgrade protection. The publish guard `flatpak_channel.py` additionally refuses to publish an older or equal version.
Rotation and revocation concept (documented, tested with temporary keys only, no production replacement key exists): (1) create the new key offline; (2) publish at least one release signed with BOTH keys and shipping the new public key in the bundle/`.flatpakrepo`; (3) later releases are signed with the new key only; (4) if the old key is compromised, publish nothing signed by it any more, ship a bundle/`.flatpakrepo` that carries only the new key and tell users to reinstall from it (`flatpak remote-delete` and re-add, or the new bundle); a client that never receives the new key cannot follow, and a Flatpak remote cannot be revoked remotely. This is a real limit, not a bug of the test.

## 5b. Windows update metadata (offline-signed) - DEVELOPMENT ONLY, not part of any release
Product decision (2026-11): Windows has no automatic update, so **no release carries `update-stable.txt` or its signature** and nothing in the release process creates them. This section is kept for the development feature `windows-self-update` (see `building-windows.md`). The Windows launcher update (`building-windows.md`) reads `update-stable.txt` and `update-stable.txt.minisig` from the latest stable release. After the release set exists: `scripts/make_update_metadata.py --version <v> --installer tsw-forever-<v>-windows-setup.exe [--previous-version <p> --previous-installer tsw-forever-<p>-windows-setup.exe]` writes the unsigned metadata (size and SHA-256 of the installers, addresses of the official release, validity at most 400 days, default 180); sign it OFFLINE with the owner's minisign key (`minisign -S -s <key> -m update-stable.txt`); attach both files to the release. The metadata is re-issued for every release (the launcher refuses expired metadata), and a previous version makes the recovery possible. The private key is never in CI.
