# Changelog

## [Unreleased]

## [0.4.0] – 2026-11-21

Feature release after `0.3.0`, the last public version: four launcher languages (French, Spanish, Brazilian Portuguese, Polish) join English and German, a floating launcher-update overlay, window limits that stay correct under `SLINT_SCALE_FACTOR` on Linux, a quiet Windows notice about newer releases, an installer update mode, and stricter Flatpak signing, mirror, delta-update and release checks, run in CI. It also contains the maintenance changes of an internal intermediate version that was never published (the GitHub Actions updates and the installer-script fix, listed under Changed and Fixed).

### Added

- Launcher languages: French, Spanish, Brazilian Portuguese (`pt-BR`) and Polish join English and German. The window (all 346 texts, including settings, installation, errors, diagnostics and update notices), the Windows installer (Inno Setup language files and the update/repair/downgrade messages), the `.desktop` entry and the AppStream summary and description carry all six languages. The system language selects the launcher language (`pt` and `pt-PT` select Brazilian Portuguese, any other language shows English); the number and percent formats follow the language. New tests keep the catalogues, the installer, the desktop entry and the AppStream data in step (`scripts/test_localization_metadata.py`, the i18n tests of `launcher-gui`). The four new translations have had no native-speaker review yet.
- Flatpak launcher updates through the Flatpak update portal: after the user agrees, the host's Flatpak installs the new version (signed, atomic, delta where available); the new version starts the next time. The main view shows an offer, progress, a restart reminder and readable errors, in all six launcher languages. It adds no sandbox permission, is silent when offline, and is off for packages without an update source (branch `local`, testing packages). User and system installations are told apart for the wording of a refusal.
- Release bundles of the stable branch know their update source: they are built from the signed repository with `--repo-url` and the repository's public signing key (`packaging/flatpak/stable-repo.gpg`; a stable bundle from an unsigned repository is refused). Bundles built without the key stay branch `local`.
- Build on push, release on tag: every push to `main` runs `build.yml` (tests, unsigned Linux repository and source archive, Windows installer, a candidate manifest with the SHA-256 of every file, and the web site); the owner's tag then publishes exactly the candidate built for that commit and compiles nothing again. The release pipeline (`release.yml`, started only by the owner's tag) signs and publishes the release inside GitHub Actions, with no manual signing or upload: the verified candidate first, then the Flatpak repository is signed in one protected job (environment `flatpak-release`, owner approval) with a signing SUBKEY (the primary key stays offline), the signed bundle and a draft release are verified, GitHub Pages (web site, signed stable repository, install files) is deployed and checked for reachability and integrity, and the draft is published only after a second owner approval (environment `release-publish`). Stable only (no testing branch or install file in the public repository); mirrored history makes static deltas possible; key management in `scripts/flatpak_keys.sh`, the signing step in `scripts/flatpak_sign_ci.sh`, the live check in `scripts/check_flatpak_live.sh`. `release-dry-run.yml` rehearses the pipeline with a throw-away key.
- Windows launcher update (**not part of the product, development feature only**, Cargo feature `windows-self-update`, never enabled in a product build; the shipped programs contain none of it): after the user agrees, the signed installer is downloaded into a fresh folder, checked through a handle that denies writing (a link or folder in place of the download is refused), and started directly (no shell) from the real path of that handle with the file locked until the installer has ended; Windows asks for the permission itself, the exit code is the result (0 installed, 2 cancelled, anything else a failure shown as such). Inno Setup closes the running launcher during a successful installation and starts the new one as the original, not elevated user; the window accepts that close request while the installer runs. A declined prompt or any failure changes nothing and is shown; the previous version can be restored from the signed metadata. Verified in a spike on a real Windows 11 machine, including the real launcher window being closed by the installer (see `scripts/windows-update-spike/HANDOVER.md`); a complete signed update through the window is not yet verified. `scripts/make_update_metadata.py` writes the metadata for offline signing.
- Windows: a quiet notice when a newer stable version exists. At start the launcher asks the official GitHub release page for the latest stable release; only when it is newer than the installed version, a small card at the bottom right of the window names the version and has one button, "Open download page", which opens that release page in the default browser (no "Later" button; it shows again at the next start). It is not an updater: nothing is downloaded, installed or run, no administrator rights are needed, and offline or any unexpected answer is silent. Pre-releases and testing builds are never offered. Windows has no automatic update by product decision; newer versions are installed by hand from the official release.
- Windows installer update mode: an existing installation is recognised (Uninstall entry of the installer's own identity); the installer then skips the licence, folder, task and Start-menu pages, reuses the folder, shows one page "TSW-Forever will be updated from version X to version Y" with the button "Update", offers a repair for the same version and warns before it replaces a newer version with an older one (a silent installation refuses unless `/ALLOWDOWNGRADE=1`); an unreadable existing installation falls back to the normal wizard. A running launcher is closed by Inno Setup's own mechanism: the installer leaves a marker file `installer-closing` in the launcher's data folder and a launcher of this version accepts the close request without its own question while the marker is fresh. Settings are never touched. English and German.
- The installed version "TSW-Forever <version>" is shown small at the bottom right of the window (taken from the build version; hidden while a launcher-update notice is shown).
- `scripts/e2e_flatpak_update.sh`: an isolated end-to-end test of the Flatpak update chain with temporary keys and a local repository (install, update, refused unsigned/foreign/corrupted updates, authorised restore, key rotation and revocation); it is also a step of `ci.yml`.
- Documentation of the one-time move from earlier bundles (branch `local`) to the update source, for user and system installations and SteamOS.
- Update channel identity, fixed when the launcher is built (`TSW_CHANNEL=stable|testing`, default `stable`). There is no setting that changes it. A stable program contains no testing endpoint, key, application ID or switching code; a testing program needs a definition file that exists only in the private development repository. A test on the finished binary and the public-source audit enforce this.
- The launcher's signed update-metadata core (strictly parsed minisign-signed metadata with channel, version, validity window and release-file address rules) is kept as a development feature only (see above); it is not part of any product build. Stable never consults testing; the original game files and the patch system are not touched.

### Changed

- Windows has no automatic update (product decision): the Windows launcher update is a development-only Cargo feature (`windows-self-update`) that no product build enables; the product launcher shows a notice and the user installs a newer installer by hand from the official GitHub release.
- The PATCHER card with the patch engine, manifest format and signing-key notice is removed from the advanced view (the client patcher is inactive; its code, checks and `tsw-launch patch status` are unchanged).
- The launcher-update notice is now a floating overlay at the bottom right of the window instead of an extra block in the main view, so the view never shifts when it appears. One card (about 340 px wide, wider only when the lettering of its buttons needs it, never wider than the window) with the dark red frame of the existing design shows every state of the update logic unchanged: offer ("Update launcher", "Later"), progress, restart reminder, "nothing to install" and errors with "Try again" (and, in the development-only Windows update, the restore button). It grows upwards with longer texts and covers what lies behind it, keeps a 14 px margin to the right and bottom edge, scrolls its text area above 190 px so that the buttons stay reachable, and swallows clicks over its own area. It is not shown in the scrolling advanced view. The Windows newer-version notice uses the same card; the small buttons have 14 px instead of 18 px of side padding so that even the French and Spanish offer stay compact (the card is about 340 px wide and widens only as far as the lettering of its buttons needs). Update logic, signatures, repositories, permissions and the fixed window size are unchanged. Tests render the window with and without the card in all six languages and every update state at 100, 125, 150, 175 and 200 % and measure position, margins, size, reachability of the buttons and of the main controls.
- New `scripts/check_flatpak_delta_update.sh` proves that a signed Flatpak repository can be updated the way a user's Flatpak does it: over HTTP, with the commit and summary signatures checked, over every static delta that targets the newest commit (a delta generated before the signing has no signature in it and is refused by clients, although `flatpak_keys.sh verify-repo` is green). `scripts/test_check_flatpak_delta_update.py` rebuilds that failure class with the real tools and runs in `build_flatpak.sh test`. The offline release (`scripts/flatpak_release_offline.sh`) runs it after the signature check and before the bundle is built, with this release's public key only: an update that would be refused by a client (an unsigned delta) stops the release with exit 21 and nothing is bundled. After a key rotation the previous public key has to be named deliberately (`FLATPAK_RELEASE_EXTRA_TRUSTED_KEYS`, or `--extra-key` of the check); it is trusted for the older commits only, listed with a warning, and never for the new state. The mirror of the live history (`scripts/flatpak_mirror_live.sh`, used by `build_flatpak.sh stable-repo`) now stops the build (exit 19) when a live repository was given and cannot be mirrored (unreachable, 404, an unsigned or untrusted signature) instead of silently building a release without parent and deltas; a verified live repository without the stable branch yet, and a build without live URL, remain first releases with their own message and exit code (`documentation/packaging.md`). `scripts/test_flatpak_release_offline.py` runs the real release script with a stub build and an intentionally broken delta path (documented in `documentation/packaging.md`).
- CI: the tests of the Flatpak signing, the mirror of the live history, the static-delta update and the release script now run in the jobs that execute `scripts/build_flatpak.sh test` instead of being skipped silently (the Flatpak tools were installed only after the tests, so 38 of them passed without running): `ci.yml` installs `flatpak ostree gnupg curl` before the tests, `flatpak.yml` and `rc-artifacts.yml` add `ostree gnupg`, and all three set `TSW_REQUIRE_TOOLS=1`, which turns a missing program into a failure (`scripts/testtools.py`, a preflight in `build_flatpak.sh test`). The CI policy check (`scripts/check_flatpak_package.py ci-policy`) enforces both for every workflow and has tests; skips that are about the state (no release set, no built repository, no game client) stay and are listed in `scripts/test_testtools.py`.
- `scripts/check_secrets_in_tree.py` scans, inside a Git repository, exactly the files a commit can contain (tracked files, new files that are not ignored, and the staged version of staged changes) instead of the whole folder, so ignored build output no longer makes it slow (about 0.3 s instead of half an hour) or report vendored runtime files. The shapes, skip lists and pinned reviewed lines are unchanged. If Git fails, the check stops with exit 2 instead of checking fewer files. `--tree` keeps the previous whole-folder scan, which is also used outside a repository. Git history and ignored files are not part of the Git mode (`prepublish_check.py --git --history` covers history). Tests: `scripts/test_check_secrets_in_tree.py`.
- The GitHub Actions of the build and release workflows are updated to Node.js 24-compatible releases, each pinned to the full commit SHA of the verified release tag: `actions/checkout` v7.0.1, `actions/upload-artifact` v7.0.2, `actions/download-artifact` v8.0.2, `actions/deploy-pages` v5.0.1 and `actions/upload-pages-artifact` v5.0.0. Permissions, triggers and security policies are unchanged.

### Fixed

- Linux: with `SLINT_SCALE_FACTOR` set (for example `1.5`), the fixed launcher window no longer ends up with limits that contradict its size. Slint 1.18 sets the window's minimum and maximum once with its own scale factor still at 1.0 and never corrects them, so the compositor was told 1000x660 for a window that really is 1500x990. The launcher now sets both limits again, to the window's physical size (logical size times the scale, rounded like the window itself), once the window exists; the window stays fixed, nothing changes without the override (a normal start and every compositor scale such as KDE at 150 % run as before), and the workaround is Linux only (`model::physical_window_limits`, guard tests in `launcher-gui/tests/window_limits.rs`; it adds the Slint feature `unstable-winit-030` as a Linux-only dependency, no new crate). Verified by the Wayland protocol at 100, 125, 150, 175 and 200 %. Not verified: whether a compositor shrinking the window because of the stale maximum was the cause of a reported cropped title, which could not be reproduced.
- The launcher's button "Start the original patcher" no longer starts a second patcher while one is still running (a burst of clicks used to start one patcher per click). A patcher that ended, or a start that failed, does not block the next start. The window tests now run in a sandbox (temporary home, a PATH with harmless stand-ins only) so that a simulated click cannot start a real program.
- `scripts/build_windows_installer.ps1 -SkipInstaller` no longer fails its own checksum self-check: with no installer to list, `SHA256SUMS-windows` is now written empty instead of holding one blank line.

### Known limitations

- At the smallest supported window size (640 x 480, only used on very small displays) the update card can partly cover other controls of the main view: with a very long error text it covers the right part of the PLAY button and, in some states, the "Skip intro videos" checkbox. The card can always be dismissed ("Later"), and the title is cut off at that width. The layout is unchanged for 0.4.0.
- The Flatpak update source starts with this release: users of an earlier single-file bundle (0.3.0 or older) must install the 0.4.0 bundle once by hand (`flatpak install --user ./tsw-forever-0.4.0.flatpak`); only from then on does the launcher offer updates. Flatpak has no background updater: the launcher looks for a newer version when it starts and while it runs, not while it is closed.
- The Windows installer is not code-signed; Windows may show a SmartScreen warning ("Run anyway" after checking the SHA-256 value). Windows has no automatic launcher update: a quiet notice with a link to the release page appears when a newer stable release exists.

## [0.3.0] – 2026-11-08

Version `0.3.0` adds the native Windows client to the shared code base. This release is produced by the automated release workflow (Linux Flatpak, Windows installer, source archive, `SHA256SUMS`). Historical private candidate notes are retained in `documentation/private-release-history.md`.

### Added

- Native Windows support in the shared Rust/Slint code base: the launcher installs or adopts The Secret World (2012) in a normal per-user-readable folder and starts the original client directly, without Wine, Proton or Flatpak. Existing installs are found in the Funcom and Steam default folders.
- The Funcom installer and patcher are never bypassed; they are started through the shell so Windows can ask for permission, and completion is recognised from the patcher log.
- Linux-only settings (Wine/GE-Proton, prefix, FPS limit and counter, shader cache, Microsoft component consent) are hidden on Windows. A warning names missing Direct3D (DirectX June 2010) libraries; the launcher downloads no Microsoft software on Windows.
- An Inno Setup installer script (`packaging/windows/`), a build script and a manual private workflow `windows.yml` that builds, tests and packages an unsigned test installer. Windows code signing is not configured.
- Windows: the first start without a usable game installation offers exactly three localized choices (download the official installer / provide an installer from disk / use an existing installation); the game folder and a three-way state (not installed / found but not confirmed complete / ready) are shown; the original installation is found through the registry entry of the original installer, with a fallback to named folders on fixed drives. Settings live in `%APPDATA%	sw-forever` (Known Folder API, migration from `tsw-launch`), larger data in `%LOCALAPPDATA%	sw-forever`.
- Windows: help for missing Direct3D libraries of the DirectX June 2010 runtime: on request the launcher fetches Microsoft's own web installer from `download.microsoft.com`, checks its hash and Microsoft signature and starts it; nothing is installed without a click and no Microsoft file is distributed.
- Windows: "Install a new copy in another folder" lets the user start a complete new installation next to an existing one; the existing installation is ignored, never touched, and the original installer is started with the new folder (`/DIR`).
- Windows: the program has no console window and carries the project icon as a resource; the installer shows it too.

### Changed

- Windows (temporary): the automatic detection of existing installations (registry, drive search, default folders, stored paths of old configurations) is paused so that a complete first installation can be tested on a machine that already has the game (`winnative::AUTODETECT_PAUSED_ON_WINDOWS`). Choosing an installation by hand works; after the launcher has started the original installer, new registry entries are recognised. Linux is unchanged.
- Windows: the frame-rate limit is not offered (it needs DXVK, which exists only under Wine); the Linux slider and switch are unchanged.
- Windows: the installer is a native x64 installer for `C:\Program Files\TSW-Forever` (path taken from Windows, custom folder on the folder page; administrator rights only for the installation, not for starting the program). There is no portable Windows ZIP; releases consist of the Flatpak, the Windows installer, the source archive and SHA-256 sums.
- Windows: the C runtime is linked statically (`.cargo/config.toml`), so the programs no longer need `VCRUNTIME140.dll` or the Universal CRT, which a freshly installed Windows 11 may not have. The build script fails if an executable imports them again.
- Version numbers are plain `MAJOR.MINOR.PATCH` everywhere: `scripts/version.py` rejects pre-release suffixes; the application is `0.3.0`, the patch-engine crate `0.1.0`.

## [0.2.0] – 2026-11-04

First public source release of TSW-Forever for Linux and SteamOS. TSW-Forever is an independent launcher for the original *The Secret World* (2012); it does not supply the game, an account, a Wine/Proton runner, or proprietary Microsoft components.

### Included

- A graphical launcher and command-line tool for installing and starting the original game in a managed Wine/Proton environment. Setup can use the checked Funcom installer download, a trusted local installer, or an existing game installation where Flatpak access permits it.
- Installation progress and completion checks based on the original patcher's evidence, with a manual verification option when automatic recognition is unavailable. The Funcom patcher may still need to be closed by the user.
- A checked GE-Proton download and a checked Microsoft DirectX June 2010 component download. The setup screen distinguishes download consent from separate acknowledgement of the linked Microsoft terms; an unchecked choice prevents provisioning. The acknowledgement is stored locally for the reviewed package and terms.
- Display settings with a game-managed default or detected resolutions applied through Wine without changing the Linux desktop mode. The existing 30–240 FPS slider, unlimited option, and optional DXVK FPS counter remain available.
- An English and German interface, title-bar navigation between the main and advanced views, and dark-theme styling.
- Flatpak packaging with app ID `org.tswlauncher.Launcher`, the matching source and required third-party licence notices. The README explains manual installation, updates, removal, and source builds.
- Prefix provenance checks, pinned download hashes, and diagnostic output filtering. Logging is optional and no telemetry is added.

### Known limitations

- The original game requires an entitled account and its own download. The original Funcom patcher may require manual closure or a verification run before the launcher offers **PLAY**.
- No automatic Flatpak update repository is currently available; install newer bundles manually. The client-patch channel is inactive.
- A previous private build was tested successfully on one Steam Machine. The public `0.2.0` build is not a guarantee of compatibility across all distributions, graphics drivers, SteamOS devices, or display setups. Windows support is future work.
